# 03 · 后端技术方案

> 目标：为管理端小程序提供 `/admin/v1` 命名空间，**复用 service，不复用 C 端 DTO**。
> 现状代码基线：`shinecar-backend`（Go + Gin + GORM，MQTT 下发设备指令）。

### 1.2 现有实现的问题

| # | 问题 | 影响 | 处理 |
|---|---|---|---|
| 1 | 所有管理接口用 `user.IsSuper` 判定，与 C 端用户表耦合 | 管理端无法独立建号 | 新建 `admin_accounts` + 独立中间件 |
| 2 | C 端 DTO 夹带营销字段（规则文案、券档位） | 管理端包体与字段不可控 | 新 DTO，service 直出 |
| 3 | `sc_orders` **没有车牌字段** | 车牌检索只能反查用户当前绑定车辆，历史不准 | 加 `plate_no` 快照 |
| 4 | 订单无停车费记录 | 无法判断是否已代缴，易重复扣款 | 只加 `parking_paid_at`（不记金额、不记流水号） |
| 5 | `config.Cfg.ParkingFee` 全局单例 | 多店接不同停车系统时需要改 | **本期不改**（所有门店共用一套停车系统）；要下沉时把 `shop_parking_configs` 作为独立迭代 |
| 6 | 整洁奖励返现失败只打日志，审核状态已置通过 | 用户拿不到钱且无标记 | 加 `reward_status` + 重试接口 |
| 7 | JWT 单 token、24h、密钥硬编码 | 无法踢下线、密钥不可轮换 | 管理端独立签发，密钥入环境变量 |
| 8 | `GetShopStationList` 未回填 `StationDetail.ID` | 自动代缴条件③失效 | 本期只记录，不修 |
| 9 | `ProcessOrderBilling` / `CalculateFee` **有副作用** | 拿它做「进行中订单试算」会消耗用户当日免费机会、核销券 | **本期不做任何金额试算**，管理端不展示进行中订单的费用；未来若要加，必须新写只读计费副本 |

## 2. 目录与非分层边界

```
internal/
  api/adminv1/               # 只做：参数绑定、DTO、错误码映射、响应包装
  service/adminapp/          # 只做：权限编排、事务、幂等、审计、聚合
  entity/admin/              # 管理端请求/响应结构（与 C 端 entity 隔离）
  middleware/adminauth/      # token 解析、账号状态、token_version、scope（预留）
  model/                     # 新表模型（gorm gen 生成）
  repo/                      # 复用现有；新增按需扩展
```

**三条硬规则**

1. handler 不写业务（不查库、不判业务规则）。
2. service 不拼 SQL（复杂查询下放 repo）。
3. repo 不判权限（权限只在 middleware + service 编排层）。

## 3. 登录与鉴权

### 3.1 时序

```
小程序                                 后端
  │ wx.login() → code                  │
  ├───────────────────────────────────►│ POST /admin/v1/auth/wx-login {code}
  │                                    │ code2session → openid
  │                                    │ 查 admin_accounts(wx_openid)
  │◄───────────────────────────────────┤
  │  ① 已绑定且 status=1               │ → { need_bind:false, token, expires_in, profile }
  │  ② 未绑定 / 账号不存在             │ → { need_bind:true, ticket }（Redis 5 分钟）
  │                                    │
  │ 用户输入 手机号 + 授权码            │
  ├───────────────────────────────────►│ POST /admin/v1/auth/bind {ticket, phone, auth_code}
  │                                    │ 校验 ticket / 账号 / 状态 / 授权码哈希 / 限流
  │                                    │ 写 wx_openid、bound_at、code_used_at、token_version+1
  │◄───────────────────────────────────┤ { token, expires_in, profile }
```

**没有 refresh token**：openid 一旦绑定，`wx-login` 本身就是静默续期（不需要授权码）。
简化实现，同时保留 `token_version` 用于强制下线。

### 3.2 Token 设计

| 项 | 值 |
|---|---|
| 算法 | HS256，密钥 `ADMIN_JWT_SECRET`（环境变量，禁止硬编码） |
| Claims | `aid`（admin_id）、`role`、`tv`（token_version）、`iat`、`exp` |
| 有效期 | 7 天 |
| 携带 | `Authorization: Bearer <token>` |
| 校验 | 解析签名 → 查账号（Redis 缓存 5 分钟）→ `status=1` 且 `tv == token_version` |
| 失效 | 退出登录 / 改角色 / 停用 / 解绑 → `token_version+1`，所有旧 token 立即失效 |

### 3.3 ticket

- 值：`{openid, created_at}`，Key `admin:bind:{ticket}`，TTL 300 秒，一次使用即删除。
- ticket 不含手机号，避免被枚举；绑定失败可重试（ticket 保留至过期）。

### 3.4 授权码

| 项 | 规则 |
|---|---|
| 长度与字符集 | 8 位；`23456789ABCDEFGHJKLMNPQRSTUVWXYZabcdefghijkmnpqrstuvwxyz`（剔除 `0O1Il`） |
| 存储 | 只存 `bcrypt` 哈希（cost 10），不存明文 |
| 生命周期 | 创建时生成 → **首次绑定成功即失效**（`code_used_at`）→ 未绑定 7 天过期（`code_expire_at`） |
| 重置 | 超管操作，覆盖哈希 + 清 `code_used_at` + 重设过期 |
| 展示 | 后台创建账号时**仅展示一次**，之后列表只显示「未绑定 / 已绑定 + 时间」 |

### 3.5 防爆破

```
Key: admin:bind:fail:{openid}:{phone}     TTL 600s   INCR
Key: admin:bind:lock:{openid}:{phone}     TTL 1800s
规则：10 分钟内 ≥5 次失败 → 锁 30 分钟；绑定成功清空计数
返回：账号不存在 / 授权码错误 / 已过期 / 已使用 → 统一「手机号或授权码不正确」
```

## 5. 能力模型

### 5.1 配置结构（存 `admin_capabilities.config`）

> 下面用 `towel_cabinet` 举例，因为它同时用到 `form + grid + 多 action`，是最复杂的形态。
> **毛巾柜本期不下发**（协议未定），这条 JSON 是「协议确认后直接 seed 就能用」的形态参考。

```json
{
  "key": "towel_cabinet",
  "scope": "station",
  "placement": "action",
  "render": "form",
  "title": "指定柜门开启",
  "subtitle": "共 20 扇柜门 · 可多选后一次开启",
  "icon": "cabinet",
  "tone": "green",
  "permission": "any",
  "sort": 60,
  "form": {
    "fields": [
      { "key": "doors", "type": "grid", "columns": 5, "total": 20, "multi": true, "stateField": "door_status" }
    ]
  },
  "actions": [
    { "action": "open",     "title": "开启", "confirm": false },
    { "action": "open_all", "title": "毛巾柜全开", "confirm": true, "confirmText": "将同时打开 20 扇柜门，请先确认现场无人靠近柜体。" }
  ],
  "command": { "target": "towel_cabinet" }
}
```

| 字段 | 取值 | 说明 |
|---|---|---|
| `scope` | `shop` / `station` | 决定出现在门店工具还是工位详情 |
| `placement` | `tool` / `action` | 工具卡（带说明）还是操作块 |
| `render` | `instant` / `confirm` / `form` / `toggle` / `page` | 5 种渲染器，未知值降级为 `confirm` |
| `route` | `device_command`（默认）/ `order_finish` / `station_maintenance` | 决定前端提交到哪个接口；**不要在前端硬编码 key 判断** |
| `tone` | `default` / `brand` / `danger` / `green` / `teal` | 图标与文字配色 |
| `permission` | `any` / `super` | 本期不参与拦截 |
| `form.fields[].type` | `text` / `number` / `chips` / `grid` | `grid` 用于柜门多选 |
| `actions[]` | 一个能力多个动作 | 底层同一 `key`，用 `action` 区分 |

**为什么需要 `route`**：开门、通风、毛巾柜是纯设备指令，走 `/commands`；
结束订单要走完整结算（`FinishOrder` 含 MQTT 联动与自动代缴），设维护要改库并同步状态，
这两者**不能当设备指令发**，否则会绕过业务逻辑。用配置里的 `route` 分流，前端只按配置调，不认 key。

> `icon` 存的是**枚举 key**（`door` / `voice` / `stop` / `wrench` / `fan` / `cabinet` / `park` / `coin`），
> 前端映射到字形或图标字体。**不要直接存「开/播/停」这类中文字**，否则以后换图标要改数据。

### 5.2 三级合并算法

```
最终能力 = 全局默认(shop_id=0, station_id=0)
         ← 门店配置(shop_id=X, station_id=0) 覆盖同 key
         ← 工位配置(shop_id=X, station_id=Y) 覆盖同 key
enabled = 0 的项不参与下发（用于「本店没有通风」这类显式关闭）
最终按 sort 升序、同 sort 按 key 字典序
```

```go
func MergeCapabilities(levels ...[]Capability) []Capability {
    merged := map[string]Capability{}
    for _, list := range levels {          // 低 → 高优先级
        for _, c := range list {
            if prev, ok := merged[c.Key]; ok { c = prev.Override(c) }
            merged[c.Key] = c
        }
    }
    out := make([]Capability, 0, len(merged))
    for _, c := range merged {
        if c.Enabled { out = append(out, c) }
    }
    sort.SliceStable(out, func(i, j int) bool {
        if out[i].Sort != out[j].Sort { return out[i].Sort < out[j].Sort }
        return out[i].Key < out[j].Key
    })
    return out
}
```

**缓存**：`admin:cap:{shop_id}:{station_id}`，TTL 10 分钟；后台改配置后按前缀删除。


> `sc_shops` 用的是 `soft_delete.DeletedAt`（`int unsigned`，`0` = 未删除），所以裸 SQL 必须显式带 `deleted_at = 0`；
> 走 GORM 时由插件自动加，不用手写。同理适用于 `sc_stations`、`sc_orders`。

**本期实际可见的按钮**：工位详情 = 开门 / 语音播报 / 结束订单 / 设为维护 / 通风全开；门店工具 = 停车缴费。
其余全靠配置增减，改数据即生效（缓存 10 分钟或手动清前缀）。

## 6. 接口清单

### 6.1 约定

```json
{ "code": 0, "message": "ok", "data": {}, "trace_id": "9f2c..." }
```

| 项 | 约定 |
|---|---|
| 鉴权 | `Authorization: Bearer <token>`，白名单只有 `auth/wx-login`、`auth/bind` |
| 分页 | 游标式：`cursor`（上一页最后一条的 `id`）+ `limit`（默认 20，最大 50），返回 `next_cursor`；`next_cursor` 为空表示到底 |
| 时间 | 请求 `yyyy-MM-dd HH:mm:ss`，响应同格式；时区 `Asia/Shanghai` |
| 金额 | **分**为整数传输（`total_fee: 1860`），前端统一 ÷100 展示 |
| 幂等 | 写操作接受 `Idempotency-Key` 头；Redis `admin:idem:{key}` 存响应 5 分钟 |
| Trace | 每个响应带 `trace_id`，同时写入 `admin_operation_log` |
| 排序 | 订单按 `start_time DESC, id DESC`；审核按 `created_at DESC, id DESC` |

### 6.2 订单车牌检索口径（重要）

`sc_orders.plate_no` 上线后：

- 有值 → `WHERE plate_no = ?`（准确、可走索引）
- 空值（历史单）→ 兜底：`WHERE user_id IN (按该车牌反查到的用户)`，并在响应里带 `plate_match: "user"`，前端不展示特殊标记（仅日志可查）

这样新旧数据都能查，且不会因为用户解绑车牌而漏单（新单）。

## 7. 设备命令

### 7.1 统一入口

```http
POST /admin/v1/stations/3/commands
{
  "key": "ventilation",
  "action": "on",
  "params": {},
  "idem_key": "3f7c1b2e-..."
}
```

```json
{ "code": 0, "message": "指令已下发", "data": { "accepted": true, "command_id": "..." } }
```

`accepted=true` 只代表**已下发到 MQTT**，不代表设备执行成功。响应不承诺结果。

**`/commands` 只处理 `route=device_command` 的能力**（纯设备指令）。映射表：

| key | action | 底层调用 | 说明 |
|---|---|---|---|
| `open_door` | `open` | `MessageSender.OpenGate(shop.SpIndex, station.StIndex)` | `command=open_gate` |
| `voice` | `play` | `MessageSender.PlayText(..., text)` | `command=ha_notice`，与现有超管语音一致 |
| `ventilation` | `turn_on`/`turn_off` | `SendCompositeCommand` | `{command:"ha_control", target:"ventilation", action:"turn_on"}`（与门禁联动现有写法一致） |
| `towel_cabinet` | `open` | `SendCompositeCommand` | **预留**：`{command:"device_control", target:"towel_cabinet", action:"open", data:{"doors":[3,7]}}` |
| `towel_cabinet` | `open_all` | `SendCompositeCommand` | **预留**：同上，`action:"open_all"`，`data:{"total":20}` |

**不走 `/commands` 的两个能力**（避免绕过业务逻辑）：

| key | route | 前端提交到 | 为什么 |
|---|---|---|---|
| `finish_order` | `order_finish` | `POST /orders/{order_id}/finish` | 需要完整结算、MQTT 联动、自动代缴、订单状态流转 |
| `maintenance` | `station_maintenance` | `POST /stations/{id}/maintenance` | 需要改 `status` 并同步 C 端可见性，且要「解除维护」的反向动作 |

> 前端 `CapabilityAction` 按 `route` 分派，不判断 key；新增同类业务能力时只加配置与接口，前端不用改。

> **毛巾柜本期只做「通道预留」**：`/commands` 里 `key → target/action` 的映射写成**查表 + 透传**（`target` / `action` / `data` 由能力配置带下来，服务端只做白名单校验，不硬编码业务分支），
> 所以本期不 seed、不实现 UI，等固件协议确认后：① seed 一条 `towel_cabinet` 配置；② 在设备侧实现同名 `target/action`。管理端不发版。
> 待确认项（毛巾柜迭代前必须与硬件定死并写回本节）：`target` 叫 `towel_cabinet` 还是 `locker`、`action` 枚举、柜门编号从 0 还是 1 起、`total` 由配置还是设备上报。
> 建议先用 `device/test` 主题在预发环境单工位验证。

### 7.2 下发前校验

```
1. 能力存在且 enabled（未 seed 的 key 一律 404「能力不存在」← 毛巾柜本期就是这条兜底）
2. 能力属于该工位/门店（防越权：不能拿 A 店配置在 B 店工位执行）
3. station.is_online = 1，否则返回 42001「设备离线，指令未下发」
4. 幂等：同 idem_key 5 分钟内直接返回上次结果
```

业务型能力（`finish_order` / `maintenance`）不走这里，各自的接口自己校验
（`finish_order` 要存在进行中订单；`maintenance` 要 `status != 4`）。

### 7.3 结果回写

MQTT 上行 `response` 消息按 `message_id` 关联。本期简化：

- 只记录「已下发」，`admin_operation_log.result = 1`（成功=已下发）
- 设备拒绝/超时由固件上行 `response`，`message_handler` 打日志即可，**不回写管理端**
- 现场兜底：运维看到工位状态没变，再点一次（幂等键保证不重复执行副作用）

> 如果固件能回传 `message_id`，P2 可加 `admin_command_records` 表做「已执行」二段式。本期不做。

## 8. 停车代缴（复用现有，不做改造）

### 8.1 为什么不改

现有 `parkingfee.PayParkingFeeByConfig(ctx, carNo)` 本身就是「按车牌直接代缴」：

- 读全局 `config.Cfg.ParkingFee`（`url` / `method` / `headers` / `form_params`）；
- 拼 `application/x-www-form-urlencoded`，**`car_no` 是唯一变量**，其余参数固定；
- HTTP 2xx 即视为已缴，**不返回金额、不返回流水号、不返回入场信息**。

停车系统没有查询接口，所以「查金额再缴」这件事在数据上不成立。因此本期：

| 不做 | 原因 |
|---|---|
| `shop_parking_configs` 表 | 所有门店共用一套停车系统，全局配置够用 |
| `POST /parking/quote` | 三方无查询能力，做了也只能返回假数据 |
| `sc_orders.parking_fee` / `parking_trade_no` | 接口不回传，记不了 |
| 代缴流水表 | 审计走 `admin_operation_log`，够用 |

> 将来某家店接了不同的停车系统，再把配置下沉为 `shop_parking_configs(shop_id, pay_url, pay_method, headers, form_params)` 并保留全局回退。
> 那时只改 `service/parkingfee` 的配置来源，接口与前端都不动。

### 8.2 本期改动（4 处）

| # | 位置 | 改动 |
|---|---|---|
| 1 | `sc_orders` | 加 `parking_paid_at DATETIME NULL`（只记时间，不记金额） |
| 2 | `service/order/service.go` `payParkingFeeForOrder` | 自动代缴成功后回写 `parking_paid_at` |
| 3 | 新增 `service/adminapp/parking.go` | `Pay(ctx, shopID, plateNo, orderID, adminID)`：防重校验 → 调 `PayParkingFeeByConfig` → 回写 + 审计 |
| 4 | 新增 `api/adminv1/parking.go` | `POST /admin/v1/parking/pay`、`GET /admin/v1/parking/records` |

C 端旧接口 `POST /admin/order/pay-parking-fee` **保留不动**，灰度期两个入口并存，稳定后再下线旧入口。

**失败语义**：非 2xx / 超时 → `41200 外部依赖失败`，**不写 `parking_paid_at`**，允许重试。
宁可重复代缴一次（门店几块钱），也不能让车主出不去闸机；超时后由人决定是否再点一次。

### 8.3 自动代缴规则（本期不改）

规则见 `01-产品与交互.md §6.2`（`FinishOrder` 后异步，三条 OR 短路：>50 分钟 / 与上一单间隔 <5 分钟 / 同店他位全忙）。

**可选修复（本期不做）**：条件③ 因 `GetShopStationList` 未回填 `StationDetail.ID` 而恒判「全部忙」，
导致「同店只有 1 个工位时必触发」。修法：`shop_service` 组装 `StationDetail` 时补 `ID`。
涉及 C 端首页弹层数据结构，建议单独排期验证，不在本期改。

### 8.4 与自动代缴的防重

| 入口 | 是否带 `order_id` | 防重规则 |
|---|---|---|
| 工位车牌行 / 订单详情 | 带 | 订单 `parking_paid_at` 非空 → `40901`；前端把按钮改成「已代缴 10-18 11:26」，再点走「仍要再缴一次」二次确认 |
| 门店工具（独立缴费页） | 不带 | 同 `plate_no` 10 分钟内二次提交 → `40902`，需带 `confirm_again=1` 重发 |

自动代缴是异步的，可能在管理员打开页面的同时完成；所以 `pay` 接口**必须**在服务端再校验一次，
不能只靠前端按钮状态。

## 9. 审计、幂等、错误码

### 9.1 审计

| 时机 | 记录 |
|---|---|
| 所有写接口 | `admin_operation_log`，`params` 脱敏后存（不存完整手机号，存 `138****8000`） |
| 资金操作 | 额外写 `sc_user_transactions`（现有），并在 log 里存 `tx_id` |
| 失败 | `result=2` + `error_msg`（截断 255），**失败也要记** |
| 事务 | 资金类操作：log 与业务同事务写；设备类：先写「已下发」再发送，发送失败更新 `result=2` |

### 9.2 幂等

```go
// 写接口统一包装
key := c.GetHeader("Idempotency-Key")
if key != "" {
    if cached, ok := redis.Get(ctx, "admin:idem:"+key); ok { return cached }
}
// 执行
redis.SetEX(ctx, "admin:idem:"+key, resp, 5*time.Minute)
```

前端对每个写操作生成 uuid，**按钮重试复用同一个 key**，用户再次点击生成新 key。

### 9.3 错误码

| 区间 | 含义 | 示例 |
|---|---|---|
| `0` | 成功 | — |
| `40100` | 未登录 / token 无效 | `请重新登录` |
| `40101` | token 已失效（version 变化） | `账号已在其他设备登录，请重新登录` |
| `40102` | 账号停用 | `账号已停用，请联系总部` |
| `40300` | 无权限 | `没有该门店的操作权限` |
| `40400` | 资源不存在 | `订单不存在` |
| `41000` | 参数错误 | `车牌格式不正确` |
| `41100` | 业务拒绝（状态不允许） | `该记录已审核过` |
| `40901` | 重复操作（订单已代缴） | `该订单已于 10-18 11:26 代缴` |
| `40902` | 重复操作（同车牌短时间重复） | `该车牌刚缴过，请确认是否重复代缴` |
| `41200` | 外部依赖失败 | `停车接口返回异常` |
| `42001` | 设备离线 | `设备离线，指令未下发` |

| 1 | `icon` 存枚举 key，前端映射 | DB 仍存枚举 key，**API 层映射成单字字形**（`fan`→`风`、`park`→`停`） | 前端把 `icon` 当文字渲染，没有图标资源 |

### 13.3 关键实现说明

**强制结束为什么必须复用 C 端 finish**：结束订单要走计费（`ProcessOrderBilling`）、扣余额、核销体验券、工位状态回空闲、MQTT 通知设备、按规则触发自动代缴。
当成「设备指令」发会绕过全部业务逻辑。所以 `adminapp` 只声明一个收窄接口：

```go
type OrderFinisher interface {
    FinishOrder(ctx context.Context, user *model.User, orderID uint64, forceFinish bool) error
}
```

传入的 `user` 是**订单归属用户**（不是管理员），`forceFinish=true` 只跳过归属校验；
扣款走 `DeductUserBalance(..., forceFinish=true)` 的语义（扣到余额为 0）。

**停车代缴的两层防重**（都不能省）：

1. 带 `order_id` → 看 `sc_orders.parking_paid_at`。自动代缴是异步的，可能管理员打开页面的同时已完成，只靠前端按钮状态会重复扣款。
2. 不带 `order_id`（门店工具入口）→ 查审计表近 10 分钟同车牌成功记录，返回 `40902`，允许 `confirm_again=1` 强行走。

失败**不写** `parking_paid_at`，允许重试。宁可重复缴一次（门店几块钱），也不能让车主出不去闸机。

**用户详情的越权防护**：`sc_users` 是 C 端全局表，门店管理员查用户前必须证明「该用户在自己门店下过单」
（`CountUserOrdersInShops`），否则遍历自增 `user_id` 就能刷全平台手机号与余额。

## 14. 实施记录（M2 补充，2026-10-24 下午）

起因是初步验收反馈的两件事：① 订单查询「有值但查不到」；② 缺「手动开单」，导致没法测结束订单。

### 14.1 `plate=undefined` —— 参数序列化踩坑

真机请求长这样：

```
GET /admin/v1/orders?phone=17354370327&plate=undefined&range=7d
```

前端明明写的是 `plate: plate.value.trim() || undefined`，但**小程序 `wx.request` 对对象形式的 `data` 会自己拼
query string，把 `undefined` 拼成字面量** `plate=undefined`。后端照收，就变成 `plate_no LIKE '%undefined%'`，
于是命中 0 条——查询条件看着有值，其实就是被这个假值卡死的。

两处都修了：

| 端 | 改动 | 位置 |
|---|---|---|
| 前端 | `request()` 发 GET 前用 `compactQuery()` 清掉 `undefined`/`null`（写操作走 JSON.stringify，本来就丢 undefined，不动） | `src/utils/request.ts` |
| 后端 | `queryText()` 把 `""` / `"undefined"` / `"null"` 一律当空，`/orders` 的 phone/plate/shop_id/status 全改用它 | `internal/api/adminv1/response.go` |

后端也要挡的原因：这一版前端改了，但用户手上还跑着旧 dist 的包；而且以后任何客户端都可能踩这个坑。

**顺带发现的真凶**：本地库里这批订单都是 2026-05 / 2025-12 的，而查询页默认 `range=7d`，
所以即使参数修好了，默认也还是 0 条。现在空结果会提示「可以切到「全部」再试一次」。

### 14.2 手动开单（代客开单）

场景：用户手机没电、不会扫码，或者车已经停进工位了，前台替他开单。

**没有引入「管理员 ↔ C 端用户」的持久绑定关系**。按手机号即查即用更贴合现场：
顾客报号码 → 查到人 → 开单，不需要提前维护一张绑定表；同一台手机也可能服务不同的店。
所谓「绑定」在实现上就是**订单一律挂到 C 端真实 user_id 上**，所以计费、余额、券、消息推送全部照旧生效。

| 接口 | 说明 |
|---|---|
| `GET /admin/v1/users?phone=13809876543` | 开单第一步：昵称、脱敏手机、余额、车辆、累计订单、**进行中订单 id** |
| `POST /admin/v1/orders` | `{station_id, user_id, plate_no?}` → 返回订单详情（可直接跳详情页） |

**为什么用 `/users?phone=` 而不是 `/users/lookup` 或 `/users/:phone`**：后者会和已有的
`/users/:user_id` 抢同一层路由。`/users` 与 `/users/{id}` 路径长度不同，不冲突。

**开单为什么必须复用 C 端 `CreateOrder`**：开单不是插一行 `sc_orders`，它包含余额校验（或体验券兜底）、
工位占用校验、Redis 分布式锁、MQTT 开机、订单通知。管理端只做 C 端没有的三件事：

```go
type OrderCreator interface {
    CreateOrder(ctx context.Context, user *model.User, shopID, stationID uint64, allowMaintenance bool) (*model.Order, error)
    SetOrderPlate(ctx context.Context, orderID uint64, plateNo string) error
}
```

校验顺序（都是「现场能立刻理解」的说法，不是笼统的系统繁忙）：

1. `41000` 车牌不是 7/8 位 → 参数先校验，别让「格式错」被「工位占用」的话术盖住
2. `40300` 无门店权限 / `40400` 工位或用户不存在
3. `41100` 工位维护中 / 已下线 / **正在使用中**
4. `41100` 该用户已有进行中订单（**带订单号**，C 端只会说「已有进行中的订单」）
5. C 端错误原样透出：`账户余额不足: userID=10, balance=0`

车牌规则：留空 → 由 C 端按「工位暂存槽位 → 用户唯一绑定车辆」的顺序取；填了 → 开单后 `SetOrderPlate` 覆盖，
写车牌失败不回滚（单已经开了、设备已经启动），只记日志 + 审计留痕。

**审计**：`domain=order, action=create_order, target=订单号, params={user_id, plate_no}`。
开单前还不知道订单号，所以失败时 `target` 是工位 id——能定位到「谁在哪个工位试过开单」。

### 14.3 前端入口

| 位置 | 行为 |
|---|---|
| 现场页 → 门店工具 → 「手动开单」 | 固定入口（不依赖能力配置），进开单页后选空闲工位 |
| 工位详情 → 空闲态卡片 → 「手动开单」 | 带上 `station_id` 直达，不用再选工位 |

开单页 `packageOrder/pages/create/index`：选工位（只列 idle）→ 输手机号查询 → 选车牌（默认第一台，
可选「不填」）→ 二次确认 → `redirectTo` 订单详情。手机号一改就作废已查到的用户，避免「换了号还开给上一个人」。

### 14.4 实测结果

| 用例 | 结果 |

## 15. 管理员开单改为「占位」（2026-10-24 晚）

> **已被 §16 取代**：这条占位路由后来确认需求本身就是错的——
> 管理员要的是「通电保养」，不是「开单」。本节作为决策历史保留，`POST /orders` 已删除。

§14.2 那版「代客开单」按用户要求整体回退。原因不是实现有问题，而是**形态定错了**：
手动开单不该是「复用 C 端完整开单流程」的业务闭环，而是管理端一条**独立的开单命令**，
它走不走余额校验、要不要启动设备、要不要绑定用户，都还没定。在规则定下来之前实现得越完整，
后面推翻的成本越高。

### 15.1 现在的位置

| 层 | 现状 |
|---|---|
| API | `POST /admin/v1/orders` 路径保留，handler 恒返回 `50100 管理员开单功能开发中，暂不可用` |
| 后端实现 | `OrderService.Create`、`OrderCreator`/`OrderOperator` 接口、`UserService.Lookup`、`GET /users?phone=` 全部删除 |
| 前端页面 | `packageOrder/pages/create` 整页删除，分包配置同步移除 |
| 前端入口 | 现场页「门店工具」→「管理员开单」、工位详情空闲态按钮，两处都保留，点击只 toast 提示 |

**为什么保留路由而不是让它 404**：404 会让人以为是路由写错或版本不对；50100 明确表达「位置在、实现没到」。
**为什么前端不发请求**：点了先转圈再弹错误是坏体验，提示是即时的；等实现落地时把 toast 换成跳转即可。

### 15.2 顺带保住的东西

这些和开单无关，都是 M2 真正需要的能力，未受影响：

- `GET /orders`（手机号/车牌/门店/时间范围检索）、`GET /orders/{id}`、`POST /orders/{id}/finish`
- `GET /users/{id}` 用户详情（余额、车辆、订单统计）
- `POST /parking/pay`、`GET /parking/records`
- `compactQuery()`：GET 查询参数里的 `undefined` 字面量修复（§14.1），这个是真 bug

### 15.3 代价

等管理员开单的规则定下来再补即可。

## 16. 管理员「通电保养」取代「管理员开单」（2026-10-24 夜）

需求重新梳理后确认：管理员要的是**给工位通电做维护保养**，不是代客开单。
上一轮之所以把两者混在一起，是因为 C 端历史上「通电」只能通过开单（`StartOrder`）间接触发，
所以出现了「要通电就得先伪造一笔订单」的荒谬路径。§15 的占位路由由此整体作废。

### 16.1 语义边界

| 动作 | 作用对象 | 是否产生订单 | 是否计费 |
|---|---|---|---|
| 结束订单 | 用户订单 | 否（关闭） | 是，按当前时长结算 |
| 设为维护 | 工位状态 `status=3` | 否 | 否 |
| **通电 / 断电** | **设备电源** | **否** | **否** |

通断电**不碰 `sc_orders`**：不校验余额与体验券、不推订单开始通知、不触发停车代缴。

### 16.2 接口

```
POST /admin/v1/stations/:station_id/power
{ "action": "on" | "off" }

→ { "station": {...含 power_state/power_at/power_by}, "message": "已下发通电指令" }
```

前置校验（按顺序）：

1. 门店权限（`requireStation`）
2. 设备离线（`stationStatus == "off"`）→ `42001`
3. 有进行中订单 → `41100 工位有进行中的订单，请先结束订单`（通电断电都拦）
4. `action=on` 且 `status != 维护中` → `41100 请先将工位设为维护中，再通电保养`

**为什么通电必须先是维护中**：工位 `status=2 + work_status=1` 时用户随时能扫码开单，
`CreateOrder` 会往这个工位发 `StartOrder`，保养到一半的设备会被用户下单启动。
维护中在 C 端本来就是「用户端下线」的语义（`CheckShopStationValid` 里只有超管能绕过），
用它当闸门不需要新概念。

**为什么断电不要求维护状态**：正确收尾是「断电 → 解除维护」。要求先解除维护会让带电的工位
提前对用户开放，反而更危险。前端在解除维护时也会反向拦截「设备还在通电」。

### 16.3 电源状态从哪来

`sc_stations` 没有电源字段；设备侧 `status_response.power_status` 只打日志、没落库、也没有主动查询链路。
所以本期**不新增字段**，用审计表推算，沿用 `LatestSetMaintenance` 的既有范式：

```go
// action IN ('power_on','power_off')，每个工位取 id 最大的一条
func (r *AdminOperationLogRepo) LatestPowerAction(ctx, stationIDs) (map[uint64]*AdminOperationLog, error)
```

DTO 因此多三个字段：`power_state`（on/off，缺省=从未操作过）、`power_at`（RFC3339）、`power_by`。

诚实地说，它记录的是「**已下发**」而不是「物理已通电」，与 `open_gate` 等命令的口径一致。
通电没有超时保护，所以前端必须持续显示「已通电 N 分钟」——这是唯一的防遗忘手段。

### 16.4 前端

- 工位详情基础操作区第 5 个按钮：`通电` / `断电`（通电态用警示色 `$warn-soft`）
- 通电态下「结束订单」禁用并提示「保养中，没有可结束的订单」
- 通电态下「解除维护」被拦截，提示「请先断电再解除维护」
- 现场页工位卡片：`repair + power_state=on` → 标签「保养中」，副标题「保养中 · 16:20 起通电」
- 现场页「门店工具」的「管理员开单」入口删除（门店级入口没有工位参数，语义不成立）
- mock 层同步 `POST /stations/{id}/power`，校验规则与后端一致

**四状态口径不变**（01 §6.1）：通电只是叠加维度，不新增状态、不参与汇总计数。

### 16.5 删除项

- `POST /admin/v1/orders` 路由与 handler（原恒返 50100）
- 前端两处 `notifyCreatePending` 占位入口
- `CodeNotImplemented`（50100）常量保留，留给 M3 使用

### 16.6 已知边界

- 不做自动断电（用户明确要求）。忘断电只能靠界面时长提醒和现场交接。
- 设备不回报执行结果，所以 `power_state` 可能与物理状态不一致；以设备为准。
