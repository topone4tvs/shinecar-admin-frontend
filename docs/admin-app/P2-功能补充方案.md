## 0. 先回答你最关心的「命令可配置」问题

你印象里的「可配置」是真实存在的，但要分清两件事，否则会踩坑：

| 层次 | 由什么决定 | 能不能配置 | 说明 |
|---|---|---|---|
| **按钮显示不显示 / 显示成什么样** | `admin_capabilities` 表（三级：全局←门店←工位） | ✅ 改数据即可，前端不用发版 | 控制名称、图标字形、排序、确认方式、placement |
| **命令能不能真正执行** | 后端 `StationService.SendCommand` 里的 switch | ❌ 硬编码，加命令要改后端代码 | 目前只认 `open_gate`/`voice`/`ventilation`/`towel_cabinet` |

**关键机制**（`station.go:359-484`）：
- `basicActions`（`open_gate`/`voice`）固定显示，不看配置表；
- 其他动作（通风/毛巾柜）**必须先在能力表里有对应 `cap_key` 且 enabled**，否则 `SendCommand` 直接返回「本工位未配置该能力」（`station.go:383-397`）——这就是「可配置」的真正含义：**配的是开关，不是命令本身**；
- 下发时用的是 `shop.SpIndex` / `st.StIndex`（补零的 `002`/`001`），与 edge 的订阅 topic 一致；
- 底层 Sender 已实现 `VentilationOn` / `TowelCabinetOpenAll`（`message_sender.go:162/168`），发到 edge 的命令 key 分别是 `ventilation_on` / `towel_cabinet_open_all`——**这两个 key 都在 edge 白名单里，能处理**。

**结论**：需求 1（毛巾柜整理、通风）的「按钮」可以纯靠能力表配置出来；但店铺维度的「一键全开」后端**没有现成接口**，必须新增（见需求 2）。

## 2. 店铺维度：一键全开门 / 一键全通电 / 一键通风

### 2.1 现状与缺口

- 后端**只有工位级** `POST /admin/v1/stations/:id/commands` 和 `/power`；
- 管理端 `api/shop.ts` 只有 `fetchCapabilities`（`GET /shops/:id/capabilities`），**没有任何店铺级批量下发 API**；
- 前端现场页「门店工具」区靠 `placement='tool'` 的能力渲染，目前只有「停车缴费」（跳转页面），没有设备命令类工具。

**所以这三个「一键」要新增后端接口**，不能只靠配置。

### 2.2 推荐方案：后端新增「店铺级批量命令」接口

```
POST /admin/v1/shops/:shop_id/batch-commands
Body: { key: 'open_gate' | 'power_on' | 'ventilation' | 'towel_cabinet', station_ids?: number[] }
```

行为：
1. 权限校验 `requireShop`（沿用现有）；
2. `station_ids` 为空 = 全店所有在线工位（`status IN (2,3)` 且未删除）；指定则逐个 `requireStation` 校验归属；
3. 逐个工位调用现有 `StationService.SendCommand` / `SetPower`（**复用现有单工位逻辑，不另写下发代码**），逐个写审计；
4. 返回 per-station 结果：`{ total, succeeded, failed: [{station_id, reason}] }`，部分成功不回滚，前端展示结果清单。

语义约束（沿用单工位规则，不新造口径）：
- **一键全通电**：`SetPower(on)` 有强约束——有进行中订单的工位会被拒绝、已通电/清洁中的会被拒绝；这些工位在 `failed` 里说明原因，不能假装成功；
- **一键全开门**：走 `open_gate`，无状态约束，但只应对在线工位下发；
- **一键通风**：走 `ventilation`，需要工位已配置该能力（否则 `SendCommand` 会拒绝）——批量时建议跳过未配置的工位并在结果里标注。

### 2.3 前端与配置

- `api/shop.ts` 新增 `sendShopBatchCommand(shopId, key, stationIds?)`；
- 现场页「门店工具」区按 `placement='tool'` 能力渲染这三个按钮——**同样由能力表控制显示**，可以给 002 店 seed 三条 `cap_key`（如 `batch_open_gate` / `batch_power_on` / `batch_ventilation`），`config.route='batch_command'`；
- 但注意：`SendCommand` 的 switch 不认这些 key，批量按钮走的是新接口，所以这批能力的 `cap_key` 只是「按钮配置」，不进入 `SendCommand` 的白名单校验。后端新接口要自己认这三个 key。

### 2.4 待你确认的口径

1. 「一键全通电」是否要对**已经有订单/正在清洁**的工位跳过（推荐：跳过并在结果里提示），还是强制断电重来（不推荐，会打断用户）；
2. 「一键全开门」是否包含**维护中**工位；
3. 批量操作是否要二次确认（推荐：是，且展示将影响的工位数）；
4. 这三个按钮是固定显示还是走能力表配置（推荐走配置，灵活）。

## 4. 用户管理页：按钮上移 + 拉黑/退款/赠款

### 4.1 现状

`src/packageUser/pages/detail/index.vue`：
- 「调整余额」按钮在模板第 76 行，位于「余额流水」之后、内容流最底部（非 fixed）；
- 调整余额弹层已支持 `grant`（发放赠送余额）和 `deduct`（扣减余额），单笔上限 1000 元、二次确认；
- 拉黑/退款**均未实现**，且后端 `admin/v1` 没有对应接口（路由只有 `GET users/:id`、`POST users/:id/balance`）。

### 4.2 方案

**（a）按钮位置上移 + 重排**：把用户操作从页面底部提到上部（用户信息卡片下方、流水之前），做成一行主操作区。顺序建议：赠款 / 退款 / 调整余额 / 拉黑。调整余额保留原弹层逻辑，只是入口位置变。

**（b）三个功能的实现路径**：

| 功能 | 后端现状 | 方案 |
|---|---|---|
| 赠款 | ✅ 已有（`POST balance` action=grant） | 独立入口，复用现有弹层，默认 action=grant |
| 退款 | ⚠️ 流水里有「充值退款」类型（`TransactionTypeRechargeRefund`），但没有独立的「退款」API | 需确认业务口径：是「扣回赠送余额」（用现有 deduct 即可）还是「真退充值款」（要走微信支付退款，属于资金操作，需新接口+严格权限）。**先按前者做，后者等你明确** |
| 拉黑 | 模型已有 `UserStatusBlack=999`；`adminapp/user.go:18` 注释明确「封禁仍走 C 端，单独排期」 | 需新增后端 `POST /admin/v1/users/:id/block`（含解封），并注意会牵动 C 端 `UserStatusCheck` 链路；前端加二次确认 |

**（c）新增 API 清单**：
- `POST /admin/v1/users/:user_id/block`（action: block/unblock）
- 退款若确认为资金退款：`POST /admin/v1/users/:user_id/refund`（需明确金额来源与支付渠道）

**待确认**：退款的真实业务含义；拉黑是否本期做（涉及 C 端链路改动）。
