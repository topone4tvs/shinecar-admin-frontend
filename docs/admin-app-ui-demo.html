登录与账号体系（两步）

新小程序与 C 端用户体系暂不打通，因此不复用 C 端 openid，也不用 is_super 判定。管理员身份独立建档，微信只作为设备身份。

① wx.login 取 code→换 openid（未绑定态）→② 手机号 + 8 位授权码→绑定 openid 并签发 token
阶段前端后端
① 微信授权静默 wx.login，不在此时索取手机号与头像POST /admin/auth/wx-login → openid_ticket（短期，5 分钟）
② 账号绑定手机号 + 授权码，输入即转大写、去空格POST /admin/auth/bind → 校验账号、写入 openid、签发 token
再次进入本地有 token 直接进；过期则静默重登POST /admin/auth/refresh，openid 已绑定则免授权码
  1. 授权码规则：8 位，数字 + 大小写字母，去掉 0/O/1/I/l 等易混字符（实际字符集约 56 个）。后台创建账号时生成，首次绑定后即失效；重置由超管操作，旧码同时作废。
  2. 服务端只存哈希：auth_code_hash（bcrypt/argon2），不存明文，后台列表也只显示「已绑定 / 未绑定」。核对失败一律返回同一句提示，避免枚举手机号。
  3. 防爆破：同一 openid + 手机号 10 分钟内 5 次失败锁 30 分钟；同一 IP 加限流；绑定成功清空计数。
  4. 两种身份要分开：admin_accounts 独立表，字段含 phone、name、role（super / shop_admin）、status、wx_openid、auth_code_hash、code_used_at；预留 user_id 可空，未来与 C 端打通时再回填，不做强关联。
  5. 门店归属：admin_shop_scopes(admin_id, shop_id)。超管不写范围即全部门店；店长只写授权门店。所有门店域接口都要校验 shop_id ∈ scope，不能只靠前端隐藏。

能力模型（预先设计）

把「有哪些按钮」交给配置，前端只认渲染类型。基础操作也走同一套，避免「固定按钮 + 动态按钮」两套逻辑。

  1. 合并规则：门店配置 + 工位配置，同 key 工位覆盖门店；enabled=false 不下发；前端按返回顺序渲染，零硬编码。

  3. 渲染器只有 5 种：即时、确认、表单、开关、跳页。遇到未知 render 降级成「确认弹窗 + 通用提交」，新设备不需要前端发版。
  4. 柜门这类「多目标」操作单独抽一个 grid 字段类型：5 列 × N 行，按 total 自动铺满，每格带 door_status（空闲 / 使用中），使用中置灰不可点。20 扇、40 扇都只是 total 不同，前端不改。全开走同能力的 open_all 动作，仍需二次确认。

旧接口 / 旧入口处理方式
POST /coupons/exchange
魔法指令		抽出 admin/service.ApplyUserAction；新接口调它，旧入口保留给 C 端超管兼容，加 deprecated 标记
POST /shop/super-command保留实现，新增 /stations/{id}/commands 做参数校验、权限过滤、幂等与审计，内部转调
GET /shop/list管理端不再用它算工位总览；新接口一次聚合工位 + 进行中订单，避免 N+1
GET /shop/station/detail返回面扩充：当前订单、用户车辆全量、能力列表；字段与 C 端解耦
/admin/order/search、/admin/recharge/*、/admin/cleanup-reward/*逻辑可复用，统一包一层 v1 handler：换 DTO、统一分页、补 shop_id 与 plate_no
  1. 三层落位：internal/api/adminv1/（HTTP、参数校验、DTO）→ internal/service/adminapp/（编排、权限、审计）→ 复用现有 repo 与设备指令层。不要在新 handler 里直接拼 SQL。
  2. 权限在 service 里判，不在 handler。能力列表按 permission 过滤，命令执行前再校验一次；否则前端改包就能越权。
  3. 写操作要幂等：结束订单、退款、代缴、开柜都带 idem_key，服务端 5 分钟内去重，避免弱网重试造成重复扣款或重复开柜。
  4. 分页统一游标：cursor + limit，订单表按时间倒序；页码分页在数据量上来后会越来越慢。
  5. 错误码分段：40x 鉴权/参数，41xx 业务拒绝（如工位维护中），42xx 设备离线；前端按码给文案，不要靠 message 匹配。

落地要点

  1. 作用域先定，再谈排布。门店切换做成「现场」页底部悬浮条，随时可切、滑动不遮挡；只刷新本页工位与门店工具。订单、用户、审核不读当前门店，因此切店不会出现「查的是全量数据、按钮却按老店能力渲染」的错位。工位详情不再放切店入口，进入时就带死 shop_id。
  2. 独立 appid = 新 openid，且与 C 端不打通。登录拆成两步：先 wx.login 拿 openid 换短期 ticket，再用手动输入的「手机号 + 8 位授权码」绑定后台预建的管理员账号。绑定成功后 openid 与账号一对一，后续静默重登不再要授权码。C 端的 is_super 不参与鉴权。
  3. 把魔法指令翻译成表单。前端不再出现 138xxxx/50 这类指令串，改成「手机号 + 金额 + 原因」的表单；后端新增显式接口，旧指令路径保留给 C 端兼容。
  4. 能力配置是唯一的「有无」开关。门店看不到毛巾柜不是前端判断的，而是接口没下发。新设备接入 = 配置一条 + 设备侧实现同一个 target/action，管理端不发版。
  5. 权限本期只建超管。所有功能对超管开放，role、门店范围、能力 permission 全部落库并出现在接口里，但不参与拦截；将来开加盟商时建 role=1 账号 + 写 scope + 打开中间件即可，接口与前端都不用改。
  6. 危险操作三重确认。弹窗 → 说明影响面 → 确认按钮用红色而非品牌色；结束后 toast + 原地回填，不整页刷新。封禁建议再填一次用户手机尾号。
  7. 操作审计先只写库，不做页面。现有只有封禁/解封日志，建议加一张 admin_operation_log：操作人、门店、工位、能力 key、参数、结果、时间。本期工位详情不展示「最近操作」，「我的 - 操作日志」也留到下一版，但写入要一开始就做——否则出了问题追溯不了。
  8. 多车牌要补一个「默认」概念。sc_user_vehicles 没有 is_default / sort，现在取 UserVehicles[0] 顺序不稳定。展示上折叠只露本单车牌、展开列全部；数据上建议加 is_default（唯一）+ sort，否则「默认车牌」每次刷新都可能变。另外订单只在开单时记录一个车牌，历史单里的其余车牌属于「账户参考」，不能当成「本单事实」展示。
  9. 订单详情需要一个新接口。/order/detail/:id 在 web.go 里是注释掉的；AdminOrderItem 不含 payment_details（余额 / 券 / 夜间优惠怎么付的）、不含 shop_id / station_id（从详情跳工位要用），plate_no 还可能为空。要展示「实付构成」，新增 GET /admin/order/detail?id= 一次返回：订单 + 支付明细 + 用户车辆 + 整洁奖励 + 代缴记录。停车费目前订单表完全没有记录，要展示代缴结果得补 parking_paid_at（只记时间，不记金额；金额由停车系统结算、接口不回传），代缴动作本身写入 admin_operation_log。
  10. 工位总览补一个聚合接口。/shop/list 的站内明细目前不带进行中订单，管理端要显示「已洗多久 / 谁在用」需避免逐个工位请求。建议 GET /admin/station/overview?shop_id= 一次返回。
  11. 车牌键盘只做一个组件。用户查询、订单筛选、停车缴费三处共用 components/PlateKeyboard：省份 8 列、字母数字 9 列，第二字符强制字母、自动过滤 I/O；输出统一为「沪A·D2311」格式，父组件只关心 v-model。不要在三个页面各写一套 input。
  12. 去掉的部分。计费规则展示、充值档位、券码兑换规则、首页营销弹窗与滚动文案、新人优惠配置，以及面向 C 端的下单 / 充值 / 绑定车牌流程，全部不进管理端。

建议拆分与节奏

先把现场跑顺，再补跨店查询与资金，最后接能力配置后台与报表。

P0 登录 + 账号绑定→现场：工位总览 + 工位详情（基础能力）→门店工具框架 + 停车缴费→能力配置表 + 通用设备命令→查询（订单列表 + 订单详情 / 用户）→审核→用户资产 + 充值退款→审计 + 报表

新增小程序目录建议：pages/login（两步）、pages/workbench（现场）、pages/station-detail、pages/query（订单 / 用户两段）、pages/review、pages/profile、pages/parking-fee；公共组件 components/PlateKeyboard、components/CapabilityAction。api/ 与 utils/request、utils/auth 可从现有前端移植后改造。
